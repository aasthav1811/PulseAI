Design Philosophy: Separate concerns into independent modules. Each NLP component is self-contained and testable. Easy to swap implementations (e.g., Transformers → VADER).

Data Flow: Raw posts → Sentiment analysis → Topic assignment → Trend calculation → Crisis scoring → Competitor extraction → Aggregated payload → Dashboard visualization

Backend Pipeline

FastAPI Server (main.py)
Async web framework handling REST requests. Bootstraps NLP models on startup, caches results, returns optimized JSON payloads for frontend.
@app.lifespan(app) async def lifespan(app: FastAPI): _bootstrap() # Generate data + run NLP pipeline yield # Cleanup (if needed) @app.get("/api/dashboard") async def dashboard(): """Return full analytics payload""" return _analysis_cache @app.post("/api/analyze") async def analyze(req: AnalyzeRequest): """Real-time single-text analysis""" analyzer = get_analyzer() sentiment = analyzer.analyze(req.text) aspects = analyzer.analyze_aspects(req.text) crisis = get_crisis_detector().score_post(req.text) return {"sentiment": sentiment, "aspects": aspects, "crisis": crisis}

Key Design: Singleton pattern for models (one instance shared across requests). Batch processing where possible. API responses pre-computed and cached.

sample_data.py

NLP Pipeline Components

🧠 Sentiment Analysis (sentiment.py)

RoBERTa pipeline with fallback to VADER. Handles sarcasm, negation, context. Aspect extraction for performance/pricing/support dimensions.

⬡ Topic Modeling (topic_model.py)

NMF + TF-IDF discovers 8 auto-labeled topics. Why NMF? Better coherence for short texts vs LDA. Fallback to keyword clustering if sparse.

📈 Trend Analysis (trend_analysis.py)

Exponential smoothing for 14-day forecast. Rolling statistics for anomaly detection (Z-score threshold). Detects sentiment inflection points.

🔴 Crisis Detection (crisis_detector.py)

Multi-signal scoring (legal, breach, outrage, viral). Engagement amplification only for critical signals. 5-tier alert system.

⚔️ Competitor Intel (competitor_intel.py)

Mention extraction, sentiment comparison, switch signal detection. Identifies competitive gaps where competitors are weak.

🔄 Fallback Systems

3-layer fallback: Transformer → VADER → Keyword. Ensures API always responds, even if GPU unavailable or model fails.

Why These Choices?

RoBERTa over BERT
Fine-tuned on 124M tweets. Handles social media language, emojis, slang better. ~15% accuracy improvement on social text vs generic BERT.
NMF over LDA
LDA assumes long documents, uses Bayesian inference. NMF with TF-IDF is faster, more interpretable, produces more coherent topics for short reviews/tweets.
Exponential Smoothing over ARIMA
ARIMA is overkill for 14-day horizon. ETS is simpler, equally effective. Fewer hyperparameters to tune.
Multi-Signal Crisis Scoring over Single Sentiment
Sentiment alone misses urgency. "Negative" could mean "slow loading" OR "company got hacked." Weighted signals distinguish noise from crises.

REST API Design

Core Endpoints

GET /api/health
Returns: {status, initialized, corpus_size, model_mode}
GET /api/dashboard
Returns: Full analytics payload (summary, topics, trends, crisis, competitors, posts)
POST /api/analyze
Input: {text, include_aspects, include_crisis}
Returns: {sentiment, aspects, crisis}
POST /api/batch-analyze
Input: {texts: [...]}
Returns: {results: [...]}
GET /api/topics
Returns: List of 8 topic clusters with keywords, sentiment distribution, examples
GET /api/trends
Returns: Time series, forecast, anomalies, trend direction
GET /api/crisis
Returns: Crisis posts, signal frequency, alert level, recommendations
GET /api/competitors
Returns: Competitor sentiment comparison, share of voice, opportunities

Design Principles: No response bloat—return exactly what frontend needs. Pre-aggregate on backend, not frontend. Cache where possible. Use proper HTTP semantics.

Key Technical Decisions

Decision: Singleton Pattern for Models
Problem: Loading BERT model on every request = 500ms+ overhead per request.
Solution: Load once at startup, cache in memory. Share across requests via module-level singleton.
Trade-off: Memory cost (~1.5GB for BERT) vs latency. Worth it for sub-50ms response times.
Decision: 3-Layer Fallback System
Problem: Model might not download, GPU might not be available, transformers might not install.
Solution: Layer 1 (Transformer), Layer 2 (VADER), Layer 3 (Keyword). Always fallback gracefully.
Trade-off: Accuracy decreases by layer, but API always responds. No better than degraded performance.
Decision: Pre-Computed Dashboard Payload
Problem: Computing all analytics on-demand = slow dashboard load.
Solution: Bootstrap entire analysis once at startup, cache in _analysis_cache dict. Frontend loads pre-computed payload.
Trade-off: Real-time data requires background job updates. Fine for demo; production needs DB + async.
Decision: Batch Processing for Sentiment
Problem: Analyzing 500 posts sequentially = 500 × 50ms = 25 seconds.
Solution: Batch 16 posts per forward pass. Reduces time to ~3 seconds (8x speedup).
Implementation: transformer.pipeline(..., batch_size=16)
Decision: Topic Name Inference
Problem: NMF returns ["slow", "load", "latency", ...] but humans need "Performance & Speed".
Solution: Map keyword sets to human-readable labels. Heuristic matching: if keywords overlap with known categories, use that name.
Fallback: Capitalize top keyword if no match ("Pricing Issues" if top word is "price").
Decision: Crisis Alert Calibration
Problem: "Dashboard is slow, considering switching" was flagged as 🔴 CRITICAL. False positive nightmare.
Solution: 5-tier signal weights. "switching" = weight 2, "data breach" = weight 10. Recalibrated thresholds: 12+ for critical (was 8+).
Result: Normal complaints = 🟡 MEDIUM. Real crises = 🔴 CRITICAL. No more alert fatigue.

Deployment & Scaling

Current: Demo mode—in-memory data, no persistence.
